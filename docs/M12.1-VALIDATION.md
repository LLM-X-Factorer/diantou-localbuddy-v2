# M12.1 Artifact Thread + Verified Revision Validation

> 验证时间：2026-08-15
> 结论：源码候选在 macOS 开发构建、确定性自动门禁和真实 Electron 界面中通过；尚未打包、发布，也不代表 WorkBuddy 六题产品基准已经通过。

## 验收范围

本轮只验收文本 Artifact 的第一条连续修订链：父产物身份、SHA-256 复核、Run 内资料快照、版本审计、失败后 replay，以及 Renderer 的 Vn -> Vn+1 交互。没有调用真实 Provider，也没有把合成资料当成业务结果。

环境：macOS 26.5（arm64）、Node.js v25.8.2、pnpm 9.15.9；Desktop 开发构建使用仓库锁定的 Electron 43.3.0。

## 自动门禁

| 检查 | 结果 |
| --- | --- |
| `pnpm check` | 168 tests；166 passed；2 个 Windows-only 合同按 macOS 平台跳过；0 failed |
| Artifact revision 定向测试 | 32 passed；0 failed |
| `pnpm build` | Renderer 18 modules 构建成功；Core TypeScript 构建成功 |
| `git diff --check` | 通过 |

确定性覆盖包括：

- 首次续改生成稳定 Thread ID 和 revision 2，后续沿父版本递增；
- Run Request v6 持久化父 Run、父文件、父 SHA-256、修改原因和内部快照路径；旧 v1-v5 仍按历史语义读取，未知未来版本 fail closed；
- 父 Artifact 被篡改时在 Provider 创建前拒绝启动，测试确认 Provider 调用数为 0；
- 父产物资料只来自新 Run 自身的 `revision-source` 快照，不依赖父 Run 的可变实时文件路径；额外资料仍须由用户重新显式添加；
- 修订 Run 失败后从头 replay，会重新复核原父 Artifact，在新 Run 生成新快照，同时保持 Thread ID 和 revision 不漂移；
- `artifact.revision_linked` 可从 JSONL 历史重建到 Desktop 投影；诊断导出保留版本和父哈希，但省略修改原因与父文件名；
- Renderer 合同禁止把 Artifact 预览正文切片后拼进 Goal，并要求用户亲自填写修改目标；进入修订时清空 Composer 遗留的旧资料选择，防止上下文串线。

## macOS 真实界面读回

使用当前源码完成 `pnpm build` 后，以独立临时 user-data 和完全合成的两版 Markdown Artifact 启动开发版 Electron。只做本机只读交互，没有点击“生成计划”，没有触发模型或外部工具。

实际读回结果：

1. V2 Run 标题、`VERSION 2`、父文件、父 SHA-256 摘要、修改原因和“查看上一版”均可见；
2. 打开 `result-v2.md` 后，本机校验预览显示 Version 2、SHA-256、字节数和正文；
3. 点击“基于此产物继续”后，Composer 显示 `V2 -> V3` 和父哈希，但 Goal 保持为空，只显示“请写清这次要怎样修改……”的提示；
4. 空 Goal 下“生成计划”保持禁用，避免把系统占位文本误当成用户修改原因；
5. 默认约束明确不读取未选择的工作区内容、不覆盖父产物，完成标准要求父 SHA-256 可追溯；
6. “查看上一版”能定位 V1 Run 并通过既有 Artifact Gate 打开 `result.md`；
7. 开发进程退出后，两个临时测试目录已精确删除；已安装版 LocalBuddy 未被操作。
