# LocalBuddy Agent 产品原则

本文沉淀可长期复用的产品经验。它不是 Changelog，也不试图罗列当前所有功能。

## 1. 一个产品对象只承担一种责任

不要再用含糊的“工作区”同时表示存储位置、证据范围、权限边界、恢复身份和协作空间。

应该明确区分：

- Project：长期组织、项目规则和共享配置；
- Thread：围绕一个持续目标积累的对话与决策；
- Run：一次不可变的执行尝试；
- Source Set：这次 Run 可以读取哪些证据；
- Worktree：某个写 Task 可以修改文件的隔离环境；
- Artifact：带身份、哈希和来源的登记产物；
- Goal Contract：结果、约束和验收标准；
- Agent Session：一条被委派的模型与工具工作线程。

只要两项责任的生命周期、权限或恢复语义不同，它们就是不同的产品对象。即使第一版 UI 把它们放在同一个页面，也不能在底层把它们混成一个字段。

## 2. 先确定范围，再按需发现，最后读取

安全顺序应该是：

```text
用户选择范围
  -> Agent 有需要时在范围内搜索
    -> Agent 读取一个相关对象
      -> Runtime 记录回执和来源
```

不要为了“以后可能用到”而提前枚举或哈希整个目录。给不必要的扫描加安全上限不是完整修复；真正的修复是删除不必要的扫描。

## 3. Checkpoint 记录真正发生的事，不记录所有可能发生的事

恢复身份应来自 Run 实际使用过的动作和证据：

- 已持久化的 Request 与 Goal Contract；
- 已验证的 Plan 与 Agent 合同；
- 已完成的工具回执；
- 成功读取证据的哈希；
- 外部副作用回执和 Artifact 身份。

无关的本地变化不应该让一条安全 Run 无法恢复。无法确认是否已经产生副作用的动作，则必须阻止自动重试。

## 4. 访问范围和审批方式是两套控制

Sandbox 决定“能碰到什么”；Approval 决定“谁来批准这次动作”。更换审批人或自动 Reviewer，不能偷偷扩大 Sandbox。

子 Agent 默认继承父 Run 的边界，可以变得更窄。要增加资料、owned paths、网络 origin 或副作用权限，必须产生新的用户可见决策。

## 5. 证据工作可以并行，文件修改必须隔离

读取、探索和独立审查通常适合并行。多个 Agent 同时修改一份可变状态，会显著增加冲突和协调成本。

因此 LocalBuddy 保持：

- 兼容的 Research Task 可以共享只读范围；
- Coding Task 使用不重叠 ownership 和独立 worktree；
- 写回主工作区只能串行 Integration；
- 全局和单 Run 都有可见容量预算。

Agent 越多不等于结果越好。每次并行都要有理由、预算和明确的合并合同。

## 6. 主控制面只保留值得决策的信息

原始日志是证据，不是正常产品体验。Run 主页面应该优先展示：

- 当前目标与计划；
- Agent 所处阶段和最近一次有效结果；
- 正在等待用户做出的决定；
- 成本、时间和失败信号；
- 已验证 Artifact 和 Review 结论。

详细事件、模型消息和工具回执继续保留给诊断，但不应该淹没主线判断。

## 7. Review 与 Implementation 必须独立

产出结果的 Agent 不应该是唯一的裁判。Review 至少需要：

- 明确审查范围；
- 默认只读；
- 继承 Goal Contract 中的验收标准；
- 带证据、按优先级排列的发现；
- 可审计的处理结果：接受、退回，或说明理由后 override。

确定性 Gate 负责状态和安全不变量；模型 Reviewer 负责语义质量。两者不能互相替代。

## 8. 兼容性变化必须按迁移处理，不能靠猜

新版本改变字段含义时，不能把旧状态悄悄解释成新语义。只能选择：

- 证明迁移后含义完全一致；
- 继续保留旧 Runtime 合同；
- fail closed，并给用户一条讲得明白的新 Run 路径。

只有版本号不够，必须把 semantic contract 本身持久化。

## 9. 测试真实问题的形状

边界值测试有必要，但不够。回归案例应该复现真实产品形状：

- 接近真实的目录规模和无关文件；
- 实际失败、中断和恢复状态转换；
- 用户真正点击的 UI 或 IPC 入口；
- 证明没有额外触发 Provider 调用或文件读取；
- 同时提供一个“什么情况下必须阻止恢复”的反例。

对于桌面产品，代码测试和最终打包 GUI 验收是两道不同门禁，不能互相冒充。

## 10. 把事件日志变成 Eval 飞轮

每个重要动作已经有事件。下一步要让这些 trace 回答：

- Agent 是否选择了允许且相关的工具？
- 是否只读取了明确选择的证据？
- Handoff 或 Approval 是否出现在正确节点？
- 恢复过程中是否重复执行了副作用？
- Artifact 是否保留来源和不确定性？

先调试单条 trace，再把稳定判断升级为 deterministic grader 和版本化数据集。每次发布前，用同一组案例比较不同版本。

## 11. 持久真源不能藏在模型 Memory 里

强制规则应该放进已提交的项目指令、规格文档，以及签名/锁定的能力包。Memory 可以帮助回忆偏好和历史背景，但必须是可选、可检查的，而且不能通过 Memory 授权权限或偷偷增加资料范围。

## 12. 学习产品合同，不复制别人的实现

外部优秀产品可以帮助我们理解：

- 哪些用户决定值得成为一等对象；
- 哪些状态转换必须可见；
- 安全与便利应该在哪里拆开；
- 长任务怎样被 steering、review 和恢复。

这不代表可以复制外部源码、资产、文案或内部协议。LocalBuddy 必须把观察重新表达为自己的领域模型，再用自己的测试证明。

## 13. Release 是一条证据链

以下结论必须分开：

1. 源码和确定性测试；
2. 当前主机打包与真实 GUI；
3. 目标平台原生 CI 与安装版合成灰度；
4. 终端用户设备与真实外部服务；
5. 生产签名、正式分发和持续反馈。

前一层通过不代表后一层通过。发布文档既要记录完成了什么，也要记录仍然开放的门禁。
