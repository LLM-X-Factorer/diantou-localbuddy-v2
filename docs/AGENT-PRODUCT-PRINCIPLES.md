# LocalBuddy Agent 产品原则

本文沉淀可长期复用的产品经验。它不是 Changelog，也不试图罗列当前所有功能。

## LocalBuddy 的产品核心

LocalBuddy 不是把 Agent、模型和工具摆到用户面前的控制台。它是一个在用户明确边界内，替用户组织多步工作，并交付可打开、可核查、可继续修改结果的本机工作台。

因此所有产品决策先接受同一个检验：

> 这个设计是在帮助用户完成任务，还是在要求用户管理 LocalBuddy 自己？

默认界面只应帮助用户回答五个问题：

1. 我想完成什么；
2. LocalBuddy 现在在做什么；
3. 是否需要我做决定；
4. 结果在哪里、是否已经检查；
5. 我下一步可以继续修改、重新开始还是退出。

第一次任务尤其不能由内部能力倒推。它应该从目标用户熟悉、低风险、短时间内可检查的工作出发，例如“把会议记录整理成可编辑 Word 纪要”；来源约束、计划审核和 Artifact Gate 在背后保证结果可信，但不应成为用户选择这个任务的理由。示例任务必须同时证明三件事：用户认得这个工作、当前版本确实能交付这种文件、LocalBuddy 的明确选材和人工确认比普通对话更有价值。

Provider、模型、Agent、并发、Skill、MCP、token、事件和 checkpoint 都是真实且重要的系统对象，但不是普通用户的默认工作对象。只有当它们影响下一步决定、安全边界、成本或故障处理时，才进入主路径。

## 1. 一个产品对象只承担一种责任

不要再用含糊的“工作区”同时表示存储位置、证据范围、权限边界、恢复身份和协作空间。

应该明确区分：

- Project：长期组织、项目规则和共享配置；
- Thread：围绕一个持续目标积累的对话与决策；
- Run：一次不可变的执行尝试；
- Source Set：这次 Run 可以读取哪些证据；
- Worktree：某个写 Task 可以修改文件的隔离环境；
- Artifact：带身份、哈希和来源的登记产物；
- Goal Contract：结果、约束和验收标准；
- Agent Session：一条被委派的模型与工具工作线程。

只要两项责任的生命周期、权限或恢复语义不同，它们就是不同的产品对象。即使第一版 UI 把它们放在同一个页面，也不能在底层把它们混成一个字段。

## 2. 先确定范围，再按需发现，最后读取

安全顺序应该是：

```text
用户选择范围
  -> Agent 有需要时在范围内搜索
    -> Agent 读取一个相关对象
      -> Runtime 记录回执和来源
```

不要为了“以后可能用到”而提前枚举或哈希整个目录。给不必要的扫描加安全上限不是完整修复；真正的修复是删除不必要的扫描。

## 3. Checkpoint 记录真正发生的事，不记录所有可能发生的事

恢复身份应来自 Run 实际使用过的动作和证据：

- 已持久化的 Request 与 Goal Contract；
- 已验证的 Plan 与 Agent 合同；
- 已完成的工具回执；
- 成功读取证据的哈希；
- 外部副作用回执和 Artifact 身份。

无关的本地变化不应该让一条安全 Run 无法恢复。无法确认是否已经产生副作用的动作，则必须阻止自动重试。

## 4. 访问范围和审批方式是两套控制

Sandbox 决定“能碰到什么”；Approval 决定“谁来批准这次动作”。更换审批人或自动 Reviewer，不能偷偷扩大 Sandbox。

子 Agent 默认继承父 Run 的边界，可以变得更窄。要增加资料、owned paths、网络 origin 或副作用权限，必须产生新的用户可见决策。

## 5. 证据工作可以并行，文件修改必须隔离

读取、探索和独立审查通常适合并行。多个 Agent 同时修改一份可变状态，会显著增加冲突和协调成本。

因此 LocalBuddy 保持：

- 兼容的 Research Task 可以共享只读范围；
- Coding Task 使用不重叠 ownership 和独立 worktree；
- 写回主工作区只能串行 Integration；
- 全局和单 Run 都有可见容量预算。

Agent 越多不等于结果越好。每次并行都要有理由、预算和明确的合并合同。

## 6. 用户注意力是一项稀缺资源

LocalBuddy 可以并发使用多个 Agent，但不应该并发争夺用户注意力。一个页面只能有一个与当前状态匹配的主要动作：开始任务、确认计划、批准具体操作、打开结果，或者处理失败。

原始日志是证据，不是正常产品体验。Run 主页面应该优先展示：

- 当前任务和正在进行的用户可理解阶段；
- 是否需要用户操作，以及不操作会发生什么；
- 已验证结果和自然的后续动作；
- 只有会改变决定时才显示的成本、时间和失败信号。

Provider、信任档、任务类型和并发使用可靠默认值；缺失配置或边界冲突发生时再就地说明。详细事件、模型消息和工具回执继续保留给诊断，但不应该淹没主线判断。

## 6.1 同一份真实过程，提供两层解释

主页面使用“任务故事”：把审计事件投影为准备、确认、并行处理、汇总、检查和完成等语义阶段，回答“现在进行到哪里”。它不能用动画或本地猜测伪造进度。

按需打开的“详细过程”使用脱敏时间序列：保留 Task、Agent、模型、工具、审批、失败和恢复的实际先后与耗时，回答“刚才究竟发生了什么”。它必须从持久事件投影生成，而不是让 Renderer 读取原始日志或业务正文。

两层视图共享同一事件真源。简单视图不能掩盖失败，详细视图也不能把内部术语重新塞回默认页面。

## 6.2 多 Agent 是执行策略，不是用户作业

用户购买的是更快、更可靠或可并行验证的结果，不是 worker 数量。只有当并行关系能解释等待时间、结果来源或失败影响时，界面才展示分工；默认使用任务标题，不显示 `worker-1`、`integrator` 等内部身份。

如果一次任务不需要并行，就不应该为了显得“像 Agent 产品”创建更多 Agent。调度器决定并发，普通用户不在每次任务前配置线程数。

## 7. Review 与 Implementation 必须独立

产出结果的 Agent 不应该是唯一的裁判。Review 至少需要：

- 明确审查范围；
- 默认只读；
- 继承 Goal Contract 中的验收标准；
- 带证据、按优先级排列的发现；
- 可审计的处理结果：接受、退回，或说明理由后 override。

确定性 Gate 负责状态和安全不变量；模型 Reviewer 负责语义质量。两者不能互相替代。

## 8. 兼容性变化必须按迁移处理，不能靠猜

新版本改变字段含义时，不能把旧状态悄悄解释成新语义。只能选择：

- 证明迁移后含义完全一致；
- 继续保留旧 Runtime 合同；
- fail closed，并给用户一条讲得明白的新 Run 路径。

只有版本号不够，必须把 semantic contract 本身持久化。

## 9. 测试真实问题的形状

边界值测试有必要，但不够。回归案例应该复现真实产品形状：

- 接近真实的目录规模和无关文件；
- 实际失败、中断和恢复状态转换；
- 用户真正点击的 UI 或 IPC 入口；
- 证明没有额外触发 Provider 调用或文件读取；
- 同时提供一个“什么情况下必须阻止恢复”的反例。

对于桌面产品，代码测试和最终打包 GUI 验收是两道不同门禁，不能互相冒充。

## 10. 把事件日志变成 Eval 飞轮

每个重要动作已经有事件。下一步要让这些 trace 回答：

- Agent 是否选择了允许且相关的工具？
- 是否只读取了明确选择的证据？
- Handoff 或 Approval 是否出现在正确节点？
- 恢复过程中是否重复执行了副作用？
- Artifact 是否保留来源和不确定性？

先调试单条 trace，再把稳定判断升级为 deterministic grader 和版本化数据集。每次发布前，用同一组案例比较不同版本。

## 11. 持久真源不能藏在模型 Memory 里

强制规则应该放进已提交的项目指令、规格文档，以及签名/锁定的能力包。Memory 可以帮助回忆偏好和历史背景，但必须是可选、可检查的，而且不能通过 Memory 授权权限或偷偷增加资料范围。

## 12. 学习产品合同，不复制别人的实现

外部优秀产品可以帮助我们理解：

- 哪些用户决定值得成为一等对象；
- 哪些状态转换必须可见；
- 安全与便利应该在哪里拆开；
- 长任务怎样被 steering、review 和恢复。

这不代表可以复制外部源码、资产、文案或内部协议。LocalBuddy 必须把观察重新表达为自己的领域模型，再用自己的测试证明。

## 13. Release 是一条证据链

以下结论必须分开：

1. 源码和确定性测试；
2. 当前主机打包与真实 GUI；
3. 目标平台原生 CI 与安装版合成灰度；
4. 终端用户设备与真实外部服务；
5. 生产签名、正式分发和持续反馈。

前一层通过不代表后一层通过。发布文档既要记录完成了什么，也要记录仍然开放的门禁。

## 14. 对标用户结果，不对标功能名

外部产品的官方文档只能定义“它承诺解决什么问题”，不能直接证明它在真实任务上做得好。产品对标必须使用同一份输入、同一段任务、同一套硬门禁和可检查产物，并明确区分：

- 官方承诺；
- 客户端黑盒观察；
- LocalBuddy 当前验证事实；
- 根据观察提出的产品推断。

基础设施能力只有在用户任务里产生可用 Artifact、可靠二次修改和可理解控制点时，才算产品能力。不能用 Agent 数、工具数、事件数或测试数代替用户结果，也不能为了追平功能表而绕过 LocalBuddy 已建立的权限、恢复和审计边界。

## 15. 版本历史是身份图，不是文件夹列表

Artifact Thread 应从持久化的父身份、revision 事件和 Artifact Registry 重建，而不是扫描工作区后按文件名或修改时间猜测。这样才能同时表达：

- V1、V2 和直接父子关系；
- failed/replay 与同版分支尝试，而不是只保留最后一次成功；
- 某一历史文件已经漂移或不可用，但审计记录仍然存在；
- diff 的两端究竟是哪两个已验证 SHA-256。

“历史仍可见”和“历史内容仍可信”是两件事。前者来自 append-only 事件，后者必须每次重新通过 Artifact Gate。任何 diff、继续修改或打开动作都不能因为 UI 已经显示过文件名，就跳过内容复核。

## 16. 富文档先做受限编译器，不让模型手写文件格式

Office 文件不是“换一个扩展名的文本”。第一条可靠链路应该把职责拆开：模型表达内容结构，本地确定性编译器负责文件格式，Artifact Gate 再从生成文件回读并核对用户可见正文。

这条边界带来四个直接收益：

- 模型不需要拼接 ZIP、XML、关系文件或二进制内容；
- 相同结构输入得到相同字节，版本和测试更容易复核；
- 可对压缩条目、展开体积、外部关系和富内容做明确 fail-closed；
- 产品可以诚实声明“支持段落、项目符号和表格”，而不是把一个偶然能打开的文件冒充通用 Word 编辑器。

视觉验收仍是独立门禁。结构回读证明正文和表格存在，不证明分页、字体、换行和单元格在目标应用里没有截断。

## 17. Agent Handoff 必须携带原始合同，不只携带摘要

Planner 的整合说明和 Worker 的结果摘要都可能丢失约束。Integrator 必须再次看到完整 Goal Contract、验收标准和不可变父 Artifact 身份；revision 还必须明确哪些内容默认保留。

父产物格式也是合同，而不是需要用户每轮重复的提示词。用户说“继续修改同一份文档”时，运行时应继承已验证文件名和格式；不能因为 Planner 省略字段就降级成 Markdown，也不能让模型输出覆盖控制器已经知道的父身份。

## 18. Grader 也是产品代码，错误的尺子会制造错误结论

真实任务失败至少有三类：产品失败、Provider/外部环境失败、评分器失败。三者必须在 trace 和报告里分开。尤其是文档标题、日期和格式检查，应先用确定性正例/反例校准，再允许编号、空白和标点等不改变语义的表达差异。

评分器缺陷不能把好产物记成产品失败，也不能在修复后把已经丢失原始证据的历史运行追溯改成通过。正确状态是 `inconclusive`，然后用修正后的 grader 开一个有新身份的新运行。

失败 trace 也必须在清理私有工作区前产出脱敏摘要：失败 Task、工具名、重试次数、失败阶段和截断后的错误原因。隐私清理仍然优先，但不能清理到只剩一个无法行动的“失败”。

## 19. Reviewer 要卡在发布之前，而且不能给自己改卷

结构合法、文件能打开和语义满足目标是三道不同门。Integrator 生成的候选应先完成确定性编译和结构回读，再由独立只读 Reviewer 比较原始 Goal Contract、Worker 证据与用户可见正文；只有接受后才能原子写入并登记 Artifact。

Reviewer 不能拥有写工具，也不能静默修自己的 finding。自动修订必须有明确上限并沿用 checkpoint 预算；恢复不能把次数清零。给 Integrator 的具体反馈属于私有运行内容，事件轨迹只保存 verdict、finding 数、候选哈希和通用失败摘要。

模型 Reviewer 仍可能误判，所以它不能替代确定性安全检查、真实 Office 打开或人工 scorecard。第一条窄切片通过后，再按 Artifact 类型扩展；不能因为 DOCX 已有 Reviewer，就宣称所有研究和代码结果都经过独立审查。

修订还有一条模型 Reviewer 之前的机械不变量：父版本必须直接提供给 Integrator 和 Reviewer，窄修改不能让正文、段落、章节或表格大幅消失。真实案例已经证明 Reviewer 会接受“修正两处错误、同时删掉八成正文”的候选。父版本保留不能只写在 Prompt 里，必须有本地可审计门槛。

## 20. Run 资料全集不等于每个 Agent 的工作集

用户批准的 Source Set 是本次 Run 的最大读取边界，不代表每个 Worker 都应该看到全部资料。计划一旦完成分工，Prompt 可见资料、工具可读资料和 checkpoint 复核资料必须使用同一份 Task working set。

只在 Runtime 拒绝越界还不够。如果 Prompt 仍列出全局资料，Agent 会把 turn 浪费在必然失败的尝试上，用户看到的只是“模型不稳定”。正确做法是先减少 Agent 看见的选择，再用 Runtime 做不可绕过的最后防线；Integrator 可以读取 Worker 结果，不必重新获得全部原始文件权限。

## 21. 安全闸门必须理解领域标识，不能只匹配标点

正则看到 2/3 很容易把它理解成除法，但在研究产物里它也可能是日期、URL 或 source-2/3/4 的资料编号。政策原文中的百分数是来源事实，也不等于模型做了派生计算。

闸门应该先剥离可验证的领域语法，再判断剩余内容是否真的需要计算底稿。每增加一条拦截规则，都要同时补“该拦的反例”和“看起来相似但必须放行的正例”。Fail closed 的目标是阻止危险状态，不是用大量误报把正常任务变成重试循环。

## 22. 能恢复成功不等于产品已经可靠

Checkpoint 让一次长任务最终到达终点，只能证明恢复协议有用。若一个普通用户任务需要多次点击继续、几十次模型调用或大量工具格式修复，产品仍然没有达到日常可用。

真实任务验收至少同时看三条：

- 结果是否满足 Goal 并能在目标应用打开；
- 中断后是否只继续未完成部分且不重复副作用；
- 为得到结果付出的调用、token、重试和用户介入是否在可接受范围。

因此成功 Run 也要保留失败计数和成本信号。下一轮优化应优先删除重复生成和不必要的模型往返，而不是把更大的 turn/token 上限当作长期方案。

## 23. Artifact Revision 默认是修改，不是重新生成

用户选择“基于此产物继续”时，产品已经知道一个已验证父版本。最可靠的做法是把父正文、结构和身份直接送到修订链，并要求候选保留未被修改的部分；让模型只根据 Worker 摘要重新写一遍，会把“修改”退化成不可控的二次生成。

保留门槛应优先捕获明显退化，例如正文骤减、段落合并、章节或表格消失；语义 Reviewer 再判断目标修改和事实是否正确。若用户确实要删掉大部分内容或完全改写，应该选择新建 Artifact，或未来使用明确的 replace 模式。不能用语言猜测悄悄关闭保留保护。

格式适配同样属于产品合同。DOCX 抽取正文中的制表符可能表示表格，二进制容器也不等于不可搜索；本地工具应该先理解受限格式，再把有界可见文本交给 Agent，而不是制造无意义的工具失败。
