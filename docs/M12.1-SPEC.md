# M12.1 Artifact Thread + Verified Revision Specification

> 状态：2026-08-15 本地实现候选，尚未发布。  
> 范围：先打通文本 Artifact 的可验证连续修订；不声称已经具备 DOCX/XLSX/PPTX 编辑器或通用 Project/Thread 产品。

## 1. 用户问题

旧版“基于此产物继续”会把预览正文截取后拼进新的 Goal 输入框。它有三个产品问题：

1. 新 Run 不知道父产物的稳定身份，只得到一段文本；
2. 用户看不到版本号、父 Run、修改原因或上一版入口；
3. 截断后的正文既可能丢上下文，也把资料传递和 Prompt 拼接混成一个动作。

M12.1 第一切片把“继续”改成 Artifact Revision。用户仍显式启动一个新 Run，但新 Run 与父产物形成可审计、可复核的版本关系。

## 2. 产品流程

```text
已验证文本 Artifact
  -> 用户点击“基于此产物继续”
    -> Composer 显示 Vn -> Vn+1 和父产物 SHA-256
      -> 用户填写本轮修改目标与完成标准
        -> Main 进程重新核对 Artifact Registry / bytes / SHA-256
          -> 复制为新 Run 的只读资料快照
            -> Run Request v6 + artifact.revision_linked
              -> Plan Review -> Workers -> 新 Artifact
```

父产物不会被覆盖。Renderer 不把预览正文拼进 Goal；Provider 只能在用户点击生成计划后，通过既有显式 Research Source 工具按需读取新 Run 的资料快照。

## 3. Artifact Revision Contract v1

Run Request v6 可选保存：

- `threadId`：由第一份父 Artifact 的 Run ID、相对文件名和 SHA-256 确定；
- `revision`：第一轮续改为 2，后续沿父版本递增；分支允许拥有相同版本号，但共享 Thread ID；
- `parentRunId`、`parentFileName`、`parentSha256`：父版本不可变身份；
- `reason`：本轮用户 Goal，经边界校验后保存；
- `sourceRelativePath`：新 Run 内部私有快照位置，不接受 Renderer 指定。

旧 v1-v5 Run Request 读取时迁移到当前内存合同，但不改写历史文件；没有 Artifact Revision 字段时保持原语义。

## 4. 安全与恢复

- 只有 Artifact Registry 中存在且当前 bytes/SHA-256 完全一致的文件才能发起修订；
- 父产物已修改、移动、删除、路径逃逸或注册表不一致时，在调用 Provider 前阻止启动；
- 新 Run 使用校验后的私有快照，不把父产物的可变实时路径作为修订资料；
- 快照进入显式 Source Set，继续使用按需读取、读取回执和 checkpoint 证据复核；
- `artifact.revision_linked` 事件记录 Thread、版本和父身份；模型与工具事件仍按原合同留痕；
- same-Run resume 复用持久合同和快照；从头 replay 重新复核父 Artifact，并在新 Run 创建新快照，同时保持原 Thread/版本身份；
- 诊断导出保留版本号和父哈希，但省略修改原因和父文件名。

## 5. Desktop 表现

- 已进入修订链的 Run 显示 `Vn`、父文件、父哈希和修改原因；
- 提供“查看上一版”入口，先定位父 Run，再使用既有本机校验预览；
- Composer 显示 `Vn -> Vn+1`，并允许取消修订关系；
- Composer 不预填一个可直接提交的假修改目标；用户必须亲自写清本轮修改要求后，“生成计划”才可用；
- 进入修订时清空 Composer 中遗留的旧资料选择；父产物快照由 Main 自动加入，需要额外资料时必须重新显式选择；
- 切换到 Coding 模式会取消待提交的文本 Artifact 修订。第一切片只支持 Research 模式；
- UI 明确说明父内容复制为只读资料快照，不再声称预览正文会被填入 Prompt。
