# M11.1 Goal Contract + Plan Review Specification

> 状态：`implemented on main; release candidate`。本增量把 Codex 基准中的“先把长期目标写成合同，再审阅执行计划”落进 LocalBuddy，但不宣称 M11 的 steering、独立 Reviewer 或多轮 Thread 已经完成。

## 1. 要解决的问题

过去一个 Run 只有一段自由文本。Orchestrator 生成计划后，Worker 立即开始，用户没有机会确认：

- 最终要交付什么；
- 哪些边界不能越过；
- 什么算完成；
- Planner 是否错误理解了资料范围、权限和任务拆分。

这会把“用户输入”“模型计划”“实际执行”压成一次不可检查的跳转。M11.1 将其拆成三个明确阶段：

```text
Goal Contract -> Orchestrator Plan -> Human Plan Review -> Workers -> Integration
```

## 2. Goal Contract

Desktop 新 Run 必须至少提供：

- `outcome`：希望交付的结果；
- `verificationCriteria`：一项或多项完成标准。

可选提供 `constraints`：来源、范围、禁止事项或格式边界。

持久化合同版本为 `Goal Contract v1 / revision 1`。每个列表最多 20 项，单项最多 1,000 字符，整个合同最多 20,000 字符。Run Request 升级为 v5，保存结构化合同，不再只保存裸 `goal`。

兼容规则：旧版调用若只提供一段 outcome，传给 Provider 和 checkpoint 的文本保持原样；只有出现 constraints 或 verification criteria 时才编译为结构化执行文本。v1-v4 Request 读取时保留原 checkpoint 身份，不重写历史文件。

## 3. Plan Review Gate

Desktop 的 Orchestrator 可以先进行一次规划模型调用。计划生成并写入 checkpoint 后，运行进入 `awaiting_plan_approval`：

- Research Worker 尚未进入 `task.started`；
- Coding worktree 尚未创建；
- Integrator 尚未执行；
- 页面显示 Goal、资料数量、信任档、扩展数量、每个 Worker 任务、owned paths、整合产物和检查命令；
- 用户只能批准当前指纹对应的整份计划，或拒绝并结束 Run。

批准指纹绑定 Goal Contract、完整 Reviewable Plan，以及 mode、明确 source paths、Provider、trust profile 和 extensions 的 scope hash。计划或范围发生任何变化，旧批准不能复用。

## 4. 持久化与恢复

每个需要审阅的 Run 保存私有 `plan-review.json`，状态为 `pending`、`approved`、`rejected` 或 `cancelled`。事件日志新增：

- `plan.review_requested`；
- `plan.approved`；
- `plan.rejected`。

应用在 pending 状态退出时，现有中断对账仍把 Run 标为 `interrupted`。恢复会从 checkpoint 取回原计划，重新计算合同和 scope 指纹；完全匹配时继续等待同一决定，不重新规划。已经批准的 Run 在后续中断恢复时可以复用同一批准。

## 5. Desktop 与非交互入口

- Desktop Main 明确启用 `requirePlanReview: true`；
- Core workflow 和 CLI 保持非交互兼容，默认 `planReview: skipped`；
- CLI 仍保存 Goal Contract v5，但不会因为没有桌面审批者而挂起；
- restart 创建新 Run、重新规划并重新审批；resume 保持同一 Run 和同一批准身份。

## 6. 安全与隐私

- Goal 和 Plan 不写入 JSONL 事件详情；事件只记录 task 数、mode 和 SHA-256；
- 结构化 Goal、Plan 和 scope 只保存在工作区私有 `.localbuddy/runs/<runId>/`；
- 脱敏诊断仍只记录 Goal 字符数，不输出正文；
- Renderer 不接收凭据；Plan Review scope 只显示数量和信任档，不显示绝对 source path。

## 7. 本增量不包含

- 在 Plan Review 页面直接编辑任务；
- append-only Goal revision 2+；
- 自动 replan 或资料/权限变化后的交互式改计划；
- 运行中 steering、暂停后追问或任意 Task 手工重跑；
- 独立 Reviewer/Critic 对计划或产物做第二模型裁决；
- 无人值守批准或绕过外部副作用 Gate。

这些仍属于后续 M11 增量，不能由“已经有批准按钮”推导为完成。

## 8. 验收合同

1. Desktop 计划生成后状态必须为 `awaiting_plan_approval`；
2. 批准事件之前不得出现 `task.started` 或 Coding `workspace.created`；
3. 拒绝后 Run 必须到 `cancelled`，不得出现 Worker 模型调用；
4. pending 状态经应用重启后必须可见、可恢复、可批准；
5. Goal、Plan 或 scope 漂移必须使旧批准 fail closed；
6. 旧 v1-v4 Request 和旧 checkpoint 的 goal identity 必须保持兼容；
7. Windows 安装版合成灰度必须实际经过“生成计划 -> 页面显示 -> 人工批准 -> Worker 执行”。

验证记录见 [`M11.1-VALIDATION.md`](M11.1-VALIDATION.md)。
