# M3.4 Research Checkpoint Resume Specification

## 1. 目标

M3.4 让异常退出的 Research Run 在安全条件成立时继续使用原 Run ID、原计划和已落盘的模型消息，而不是只能从原始 Request 全量重放。

本阶段不覆盖 Coding Run。Coding 的 worktree 副作用、检查命令、patch 与 Integration Proposal 需要独立恢复协议，不能把 Research 的文件只读/Artifact 写入假设直接套用。

## 2. 持久化布局

每个 Research Run 在 `.localbuddy/runs/<run-id>/checkpoint/` 保存：

```text
manifest.json                  # Run、goal、workspace snapshot、validated plan
tasks/<task-id>.json           # Agent contract、messages、phase、turn、tool cursor、output
tools/<task-id>/<call-hash>.json # started/completed receipt 与完成结果
artifacts.json                 # Artifact Registry
calculations.json              # deterministic calculation registry
```

所有 JSON 更新先写同目录唯一临时文件，再原子 rename。单个 Task checkpoint 上限 10 MiB；Task/Agent ID 必须满足本地安全标识符约束。

这些文件会包含用户目标、Prompt、模型消息和工具输出，属于本地私有运行状态；API Key 不写入 checkpoint、event log 或 Artifact。

## 3. Run 固定契约

Planner 完成后、Worker 开始前写入 manifest：

- Run ID、canonical workspace、mode=`research`；
- goal SHA-256，不保存第二份可编辑 goal；
- 已经过本地 schema 校验的 Research Plan；
- workspace SHA-256、条目数和快照是否完整；
- contract version 与时间戳。

工作区快照按稳定排序哈希相对路径、类型和文件内容，忽略 `.git/`、`.localbuddy/`、`node_modules/` 与符号链接。为防止无界扫描，最多接受 1,000 个条目；超过上限仍可正常运行，但 checkpoint resume 标记为不可用。

## 4. Task 状态机

每个 Task 独立保存如下 phase：

```text
ready_for_model
  -> model_inflight
  -> tool_inflight -> ready_for_model
  -> succeeded
```

Task contract SHA-256 覆盖 Task 定义、Agent 身份/角色/能力/指令和可用工具 schema。消息只能追加，turn 不能后退，`succeeded` 不能重新打开。Integrator 的 dependency outputs 会进入初始 user message，因此已完成 Worker 输出会随 Integrator checkpoint 固定。

恢复策略：

| 中断边界 | 行为 | 原因 |
|---|---|---|
| Task `succeeded` | 直接恢复 output，不执行 Task | 结果已完整落盘 |
| `ready_for_model` | 使用已落盘 messages 发起下一次请求 | 没有待确认副作用 |
| `model_inflight` | 从请求前 messages 重试模型 | 远端请求结果不确定，但没有本地副作用；可能重复计费 |
| 已完成工具回执、消息游标未推进 | 复用回执结果并推进游标 | 避免重复工具副作用与工作量 |
| 只读/计算工具只有 started 回执 | 重新执行 | 工具契约无本地写副作用 |
| 写入/执行工具只有 started 回执 | 阻断 checkpoint resume | 无法证明上次副作用是否发生 |

## 5. 工具回执

工具经本地 allowlist、参数 parser 与角色审批后，执行前写 started receipt。回执身份固定：Run、Task、Agent、tool-call ID、工具名、参数哈希和风险级别。

执行结果先原子更新为 completed receipt，再追加 `tool.completed`/`tool.failed` 事件并推进 Task 消息游标。若进程在这些动作之间退出，下一次执行用完全相同的工具身份读取 completed result，并追加 `tool.reused`；身份或结果冲突一律报错。

Artifact 写入和确定性计算登记使用持久化、幂等注册表。相同主键与相同内容可复用，不同内容视为状态冲突。

## 6. Desktop 恢复流程

Desktop 对账到非终态 Research Run 后：

1. 追加 `run.interrupted`，同时投影 checkpoint 可用性、已完成 Task 数和待恢复 Task 数；
2. 用户可选择“从 checkpoint 继续”或“从头重新运行”；不会自动产生新的模型成本；
3. checkpoint resume 重新验证 Request、workspace、goal、manifest、计划、Task/Agent/工具契约和含糊工具回执；
4. 全部通过后在原 Run 追加 `run.resumed`；
5. Scheduler 为每个 Task 追加 `checkpoint.restored`，跳过已完成 Task 并调度未完成 Task；
6. 后续继续追加正常 task/model/tool/artifact 和 Run 终态事件。

若恢复后再次发生进程退出，最新生命周期事件仍为 `run.resumed`，下次 Desktop 对账可以再次追加 `run.interrupted` 并重新检查最新 checkpoint。

## 7. 阻断与降级

下列情况在 `run.resumed` 前阻断：

- workspace 内容与创建 checkpoint 时不同，或快照超过上限；
- Request/goal/workspace/Run ID 不一致；
- manifest、消息、工具回执或注册表损坏；
- 计划出现未知 Task，Task/Agent/工具契约发生变化；
- 写入或执行工具留下 started、没有 completed 回执。

阻断会追加 `checkpoint.resume_blocked`；原 `interrupted` 历史和 M3.3 的 replay 入口仍保留。

## 8. 非目标

- 不恢复 Provider 服务器内部状态或 continuation token。
- 不保证 model-inflight 请求不重复计费。
- 不支持 Coding Run checkpoint resume。
- 不跨 Desktop/CLI 进程共享锁或自动接管仍存活的 CLI Run。
- 不处理机器断电造成的文件系统损坏，也不把原子 rename 等同于磁盘 fsync 保证。
- 不自动执行被判定为含糊的写入/执行工具。
